2.2 DI × Scope 架构（agent-core-v2 核心）

传统 DI 容器只有一个全局作用域，无法处理多会话、多 Agent 场景。v2 引擎设计了 4 层 LifecycleScope：

App → Workspace → Session → Agent
Scope生命周期注册的服务可见性
App进程级配置、插件管理、MCP 管理、Session Index全局
Workspace工作区级文件系统、Git、MCP 连接池、Skill CatalogApp 可见
Session会话级消息历史、Token 计数、Agent 生命周期App + Workspace 可见
AgentAgent 级工具注册、状态、Goal、CronApp + Workspace + Session 可见

核心规则：

  • 父作用域不能依赖子作用域（App 不能依赖 Session）
  • 子作用域可以注入父作用域的服务（Agent 可以注入 App 的全局配置）
  • Scope 关闭时自动反向级联清理所有子资源

2.2.1 DI 容器实现

// 服务注册（src/_base/di/instantiation.ts） export const ISessionService = createDecorator('sessionService'); // 服务实现（src/session/sessionService.ts） export class SessionService extends Service implements ISessionService { constructor( @ISessionIndex private readonly index: ISessionIndex, @IWorkspaceLifecycleService private readonly workspaceLifecycle: IWorkspaceLifecycleService, ) { super(); // 构造函数内只能调用 provide/on/effect } } // 作用域注册（src/session/sessionService.ts） registerScopedService( LifecycleScope.Session, ISessionService, SessionService, ScopeActivation.OnScopeCreated, 'session', );

2.3 Agent 循环（Plan/Act/Observe/Reflect）

User Input→ Prompt→ LLM Call→ Tool Selection→ Permission Check→ Tool Execute→ Observe Result→ Reflect→ Next Turn or Output

Loop 实现位于 packages/agent-core/src/loop/：

  • llm.ts：LLM 调用管理，重试、超时、Token 统计
  • turn-step.ts：单步执行，工具调用调度
  • run-turn.ts：完整 Turn 执行，包含 Plan 模式检查
  • tool-call.ts：工具调用执行，权限检查

2.4 权限系统

基于 Chain of Responsibility 设计模式，8 个策略串行执行：

PermissionChain (src/agent/permission/) ├── 1. auto-mode-approve — auto 模式下自动批准 ├── 2. yolo-mode-approve — yolo 模式下跳过审批 ├── 3. goal-start-review-ask — Goal 启动时询问 ├── 4. exit-plan-mode-review-ask — Plan 模式退出时审查 ├── 5. session-approval-history — 历史审批记录 ├── 6. user-configured-rules — 用户自定义规则 ├── 7. auto-mode-ask-user-question-deny — auto 模式下拒绝提问 └── 8. path-access-policy — 文件路径访问策略

3 种权限模式：

模式行为
manual每个工具调用都需要用户确认
auto只读工具自动批准，修改工具需审批
yolo所有工具调用自动批准（包括 Bash）

3.3 上下文管理

上下文窗口管理是 Agent 系统的核心挑战。NightHawk 使用三层压缩策略：

3.3.1 微压缩（Micro Compaction）

位置：packages/agent-core/src/agent/compaction/micro.ts 策略：丢弃冗余的中间步骤 - 保留：用户消息、Assistant 最终回复、工具调用签名 - 丢弃：工具调用的完整输出（保留摘要） - 触发：每 N 个 Turn 后自动触发

3.3.2 全量压缩（Full Compaction）

位置：packages/agent-core/src/agent/compaction/full.ts 策略：结构化摘要 - 将历史消息压缩为结构化摘要 - 保留：关键决策点、文件路径、错误信息 - 丢弃：详细对话过程 - 触发：用户手动 /compact 或上下文窗口接近限制

3.3.3 Handoff 压缩

位置：packages/agent-core/src/agent/compaction/handoff.ts 策略：SubAgent 结果压缩 - SubAgent 返回的完整结果被压缩为摘要 - 保留：结论、关键发现、错误 - 丢弃：中间推理过程

4.2 SecurityScan 规则引擎

  • 每条规则继承 SecurityRule 基类
  • 规则接口：match(file: SourceFile): Finding[]
  • Finding 包含：severity、cwe、owasp、message、location、fix
  • 支持多语言：JavaScript/TypeScript、Python、Go、Rust、Java、C/C++

4.3 SecretScan — 密钥检测

  • 两级检测：正则模式匹配 → Shannon 熵评分
  • 正则模式：API Key、Token、私钥、密码等 50+ 模式
  • 熵评分：对匹配到的字符串计算 Shannon 熵，高于阈值才报告
  • 误报率控制：白名单、上下文检查

4.4 TaintTrace — 污点追踪

  • 变量级追踪：追踪用户输入到危险 sink 的完整数据流
  • Source 标记：用户输入、HTTP 请求、文件读取
  • Sink 标记：eval、exec、SQL 查询、文件写入、Shell 命令
  • 传播规则：赋值、函数调用、返回值

4.5 DepAudit — 依赖审计

  • 三种模式：离线（本地规则）、OSV（Open Source Vulnerabilities）、包管理器（npm audit）
  • 检测：未锁定版本、已知漏洞、恶意包

六、关键技术决策

6.1 为什么 DI × Scope 而非传统 DI？

问题：传统 DI 容器（如 NestJS、Angular）只有一个全局作用域。NightHawk 需要同时管理多个 Workspace、Session、Agent，每个都有自己的生命周期和状态。

方案：4 层 LifecycleScope，每层有独立的容器实例。

优势：

  • 天然映射自然生命周期：App（进程）→ Workspace（工作区）→ Session（会话）→ Agent（Agent）
  • 子 Scope 自动继承父 Scope 的服务，无需手动注册
  • Scope 关闭时自动级联清理，无内存泄漏
  • 每个 Agent 拥有独立的工具注册、状态、Goal

6.2 为什么两套引擎（v1 + v2）？

历史原因：v1 引擎（agent-core）是早期设计，采用传统 DI 服务层。随着多会话、多工作区需求，v2 引擎（agent-core-v2）从零开始设计了 DI × Scope 架构。

共存策略：

  • v1 保留用于 TUI 和旧版 ACP 兼容
  • v2 是当前主力引擎，负责 kap-server 和新功能
  • SDK 层（node-sdk）透明切换：SDKRpcClientV2 封装 v2 差异
  • klient 契约驱动 facade，统一 v1/v2 的客户端接口

6.3 为什么 Node.js SEA 而非 pkg/nexe？

方案优势劣势
Node.js SEA官方方案，无第三方依赖，支持所有 Node.js API二进制体积较大（~134MB）
pkg体积小已废弃，不支持 ESM
nexe体积小维护不活跃，兼容性问题

6.4 为什么自研 pi-tui 而非 Ink/React-Terminal？

  • 零依赖：不依赖 React、JSX、虚拟 DOM
  • 直接操作终端缓冲区，极致性能
  • 完整的 Canvas、动画、事件系统
  • 支持真彩色、Unicode、鼠标事件
  • 专为 NightHawk 的 TUI 需求定制

6.5 为什么用 Changesets 而非 Semantic Release？

  • Changesets 更轻量，适合 monorepo
  • 自动生成 changelog，支持多包版本管理
  • PR 驱动的发布流程：创建 changeset → 合并 → 自动发布
  • Semantic Release 依赖 Angular Commit 规范，约束太强
