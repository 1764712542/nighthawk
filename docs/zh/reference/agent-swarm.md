# AgentSwarm 集群模式

AgentSwarm 是 NightHawk 的集群模式，允许同时启动多个子 Agent 并行处理任务，大幅提升大规模任务的执行效率。

## 概述

AgentSwarm 与普通 Agent 的核心区别：

| 特性 | 普通 Agent | AgentSwarm |
|------|-----------|------------|
| 并发数 | 单个子 Agent | 最多 128 个并行子 Agent |
| 任务分配 | 单一线程 | 模板分发，自动拆分 |
| 启动方式 | 模型自主决策 | 显式调用 `AgentSwarm` 工具 |
| 适用场景 | 单点探索、代码修改 | 批量扫描、大规模审计、并行审查 |

## 工作原理

AgentSwarm 通过一个 **prompt 模板** 和一个 **items 列表** 工作：

1. 模板中的 `{{item}}` 占位符被 items 列表中的每个值替换
2. 每个替换后的 prompt 分配给一个独立的子 Agent 执行
3. 所有子 Agent 并行运行，互不干扰
4. 结果汇总后返回给主 Agent

## 使用场景

### 批量安全扫描

```
扫描以下目录中的 SQL 注入漏洞：{{item}}
```

items: `["src/api/", "src/admin/", "src/auth/", "lib/", "config/"]`

→ 5 个子 Agent 同时扫描不同目录，速度提升 5 倍。

### 大规模代码审查

```
审查以下文件是否存在安全风险：{{item}}
```

items: `["src/handler/users.ts", "src/handler/orders.ts", "src/handler/payments.ts", ...]`

→ 一次性审查所有关键文件。

### 并行渗透测试

```
对 {{item}} 进行端口扫描和服务枚举
```

items: `["192.168.1.1", "192.168.1.2", "192.168.1.5", "10.0.0.1"]`

→ 同时扫描多个目标主机。

## 与 SubAgent 的区别

AgentSwarm 和普通的 SubAgent（子 Agent）虽然都是并发执行，但设计目标和适用场景不同：

| 维度 | SubAgent（子 Agent） | AgentSwarm（集群） |
|------|---------------------|-------------------|
| **启动方式** | 主 Agent 在任务执行中**自主决定**是否派发 SubAgent | 主 Agent **显式调用** `AgentSwarm` 工具 |
| **任务来源** | 主 Agent 根据上下文动态生成任务描述 | 通过 `prompt_template` + `items` 列表**批量分发** |
| **并发模型** | 单个 SubAgent 执行单一任务；主 Agent 可同时派发多个 SubAgent，但各自独立 | 一次调用同时启动 **N 个** 子 Agent，共享同一模板 |
| **适用场景** | 代码审查、探索性分析、单点修复 | 批量扫描、大规模审计、并行渗透测试 |
| **任务粒度** | 一个 SubAgent 处理一个完整子任务 | 一个集群处理一批同类子任务 |
| **结果处理** | SubAgent 返回单一结果 | 集群返回 N 个结果，由主 Agent 合并 |
| **上下文共享** | 各 SubAgent 上下文完全隔离 | 同一模板确保各子 Agent 任务结构一致 |
| **最大并发** | 由主 Agent 的资源决定 | 最多 **128** 个并行子 Agent |

### 典型选择

- **用 SubAgent**：当任务需要动态决策、探索性分析，或者各子任务差异较大时。例如"审查这个 PR 的变更"、"探索这个不熟悉的模块"。
- **用 AgentSwarm**：当有一批结构相同的任务需要并行执行时。例如"扫描这 50 个目录的漏洞"、"枚举这 20 个主机的端口"。

两者可以组合使用：主 Agent 在渗透测试中先用 AgentSwarm 批量扫描，再对发现的问题用 SubAgent 逐个深入分析。

- **最大并发数**：128 个子 Agent
- **超时时间**：每个子 Agent 最长 2 小时
- **上下文隔离**：每个子 Agent 拥有独立上下文，互不干扰
- **结果合并**：子 Agent 返回结果后由主 Agent 汇总

## 注意事项

- AgentSwarm 不适用于需要共享状态的任务
- 每个子 Agent 独立消耗模型 token，注意配额管理
- 子 Agent 之间不能互相通信
- 结果由主 Agent 汇总，可能存在信息丢失风险
